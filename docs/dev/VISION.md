# mbt-map Vision

mbt-map の設計の拠りどころ。いまも効いている目標・予算・原則・方針と、これからの計画だけを置く。Phase 0〜20 の計画と経過（各 Phase の範囲と完了条件、計測、予算を上げた経緯、ほかのライブラリとの機能の突き合わせ）は、前のリポジトリ `t-ujiie-g/mbmap` の VISION.md・PROGRESS.md と、このリポジトリの [PROGRESS.md](../../PROGRESS.md) にある。いまある仕組みの説明は [ARCHITECTURE.md](ARCHITECTURE.md) とその分冊にある。

## 1. ゴール

MoonBit で書いた、**サーバーに頼らない WebGIS の実行基盤**（フロントエンドで完結する GIS ライブラリ）。表示・データ加工・解析・3D がブラウザ内で完結し、**使う分しか読み込まない**。

| 柱 | 中身 | 位置づけ |
|---|---|---|
| 表示 | 2D のベクトルタイルとラスタ、ラベル、GeoJSON、地形、地球表示、3D（建物の押し出し、glTF、3D Tiles、I3S、点群） | 入口。軽く、速く。3D は表示モードの 1 つとして扱う |
| データ | 形式の読み書き（GeoJSON、CSV、Shapefile、FlatGeobuf、KML、GeoTIFF など）、GIS の Web サービスの読み込み、座標系変換 | 解析と表示をつなぐ土台 |
| 解析 | 空間索引、計測、空間関係、集計、ジオメトリ演算、ラスタ解析、経路探索 | Worker 上の Wasm で動かし、メインスレッドを塞がない |
| ヘッドレス UI | 地図の操作、検索、計測、凡例、レイヤー一覧、属性テーブル、作図・編集などを、**見た目を持たない API**（状態・操作・イベント）として渡す | 見た目は作り手が自由に作る。組み立て済みのウィジェットは作らない |

- 機能の網羅は目指さない。各柱で、ブラウザ内で完結させる価値が大きいものから作る。サーバー側の機能が欠かせないものは作らない（§5）。
- **特定の UI フレームワークに依存しない**。地図は「canvas を受け取って描く命令的なエンジン」とし、UI フレームワークとの統合は外側の薄い層で行う。
- 使い方の優先順位：
  1. **TS/JS から**（最優先）：npm パッケージ `mbt-map`。型定義（`.d.ts`）付きの ESM。
  2. **Web Component**（`<mbt-map>`）：どのフレームワークからも使える共通の受け口。
  3. **MoonBit から**：mooncakes の `t-ujiie-g/mbtmap`（npm の実装の上の型付きの API）と、rabbita 向けの `t-ujiie-g/mbtmap_rabbita`（§6）。
- 計算コアは純 MoonBit で書き、どのバックエンド（wasm / wasm-gc / js / native）でもテストが通ること。

## 2. 性能目標とサイズ予算（常に計測する）

| 指標 | 目標 |
|---|---|
| 1 タイルのデコード＋テッセレーション（z14 都市部） | bench fixtures の中央タイル 4.6ms 以下、35 タイルの中央値 11.7ms 以下 |
| フレーム時間 | 60fps、パン・ズーム中の GC 停止なし。代理指標：1 フレームの描画 CPU 時間 p95 が 1.44ms 以下、20ms 超のフレーム 0 |
| 初回描画まで | 215ms 未満 |

上の値は、同じハーネス・同じスタイルで測った基準（MapLibre GL JS 6.16.0。デコードはその 1/2、初回描画はそれより短く）から決めた。測定条件は `bench/` と前のリポジトリの PROGRESS.md にある。中級の Android 端末の実機計測は当面行わない。

サイズ（gzip）は入口ごとの予算で守る。**正は `npm/scripts/size.mjs`** で、CI が予算と入口の間の参照の制限を確かめ、超えたら失敗させる。主なもの：

| 入口 | 予算 |
|---|---|
| `mbt-map`（表示、メインスレッド側） | 168KB |
| 表示用 Worker（Wasm 含む） | 100KB |
| `mbt-map/element` | 5KB（`mbt-map` の上に） |
| `mbt-map/ui` | 全部入りで 10KB、コントローラ 1 つ 2KB |
| `mbt-map/search` | 5KB |
| `mbt-map/draw` | 10KB |
| `mbt-map/services`、`mbt-map/analysis`、`mbt-map/data`、`mbt-map/geodesic`、`mbt-map/3d` | 12KB、9KB、6KB、2KB、10KB（それぞれの Worker と Wasm は別の行） |

- **表示しか使わない利用者のバンドルは、ほかの入口を足しても 1 バイトも増えない**こと。
- 新しい入口やモジュールは、作るときに測ってから予算を決め、`size.mjs` に行を足す。予算の変更はユーザーの判断で行い、PROGRESS.md に記録する。
- 数値はすべて `bench/` の再現できるスクリプトで出し、結果の JSON（`bench/results/`）から書く。体感や推測で「速い」と書かない。

## 3. アーキテクチャの原則

パッケージと入口の一覧、依存の向きの全体、タイルの流れは [ARCHITECTURE.md](ARCHITECTURE.md) にある。ここには、変えるならユーザーの確認が要る決まりだけを置く。

- **依存は一方向**：`core` から表示の `map`、その外の `npm`・`element` へ向かい、逆方向の依存を作らない。`map/` 以下のパッケージは、いかなる UI フレームワークにも依存しない。
- **メインスレッドはジオメトリを触らない**（§4-3）。デコード、スタイルの評価、テッセレーションは Worker の Wasm が行い、出力のバッファをそのまま GPU へ渡す。
- **入口の分割と遅延ロード**：npm パッケージは 1 つ（`mbt-map`）のまま、subpath exports で入口を分ける。`import` しない入口はバンドルに入らない。データ・解析・サービス・3D の Wasm は表示用 Worker とは別のモジュールにし、初めて使うときに読み込んで専用の Worker で動かす。API は Promise を返す。
- **Wasm は入口ごとに 1 つ**を基本にする。ある機能群の固有のコードが gzip で約 20KB を超えたら、別のモジュールに切り出す。表示用 Worker に解析を入れる一体型にはしない。
  - 根拠（計測）：wasm-gc のモジュールを増やす固定費はほぼ 0（空のモジュールで 0.18KB）だが、core の共通のコード（三角関数、整数の文字列化など）がモジュールごとに約 6KB 重複する。読み込みは 1〜2.5ms、Worker の起動は 2〜6ms で、一体型と実行速度は変わらない。
- **データの共通形式は列指向**：内部の受け渡しは、GeoArrow 互換の列指向レイアウト（座標・オフセット・属性を列ごとの型付き配列）を ArrayBuffer として持ち、transfer する。読み込み → 解析 → 表示がコピーなしでつながり、解析の結果はそのまま描画のソースになる。レイアウトは `geom/table.mbt` と [FORMATS.md](FORMATS.md) にある。
- `map/` とファサードは、データ・解析・サービス・3D の入口を import しない。それらは表示に依存せず、表示とは列指向のバッファだけでつながる。

## 4. 高性能化の設計原則

1. **ホットパスでアロケーションしない**。頂点・インデックスは事前に確保した `FixedArray`/`Bytes` に書き込む。Struct-of-Arrays を基本とする
2. **頂点は量子化**：タイル内座標を `TILE_EXTENT`（8192、MapLibre の `EXTENT` と同じ）に換算して Int16 で持つ。属性もできるだけ UInt8/Int16 に正規化する
3. **ゼロコピー転送**：Worker の出力はそのまま `ArrayBuffer` として transfer し、メインスレッドでは `bufferData` するだけ。メインスレッドでジオメトリを触らない。表示用 Worker は wasm-gc（wasm・wasm-gc・js を実測して決めた。[TOOLCHAIN.md](TOOLCHAIN.md)）
4. **描画コール削減**：タイル×レイヤー単位でバッファを結合し、VAO を使い回す。同じ形のレイヤーはバッファを共有する
5. **フレームループは差分駆動**：カメラ・データが変わらないフレームは描画しない
6. **遅延と予測**：表示範囲外の地物はデコードしない。ズーム遷移中は親/子タイルで穴埋めする
7. **Worker プール**：ハードウェアのスレッド数の半分、1〜4。リクエストに優先度を付け、見えなくなったタイルは取り消す
8. **使う分しか読み込まない**：機能は入口ごとに分け、Wasm も入口ごとに遅延ロードする。入口ごとのサイズ予算を CI で守る
9. **データは列指向のまま流す**：読み込み・解析・描画の間で、地物単位のオブジェクトを作らない。重い処理は Worker 上の Wasm で行う
10. **3D を見越したカメラと座標**：カメラは bearing・pitch・高さを持つ 4×4 行列で表し、描画はタイルや中心からの相対座標で行う（float32 の精度不足を避ける）

## 5. スコープ

いまある機能は [docs/](../README.md)（入口ごとのガイド、[style-support.md](../style-support.md)）と ARCHITECTURE.md にある。ここには、線を引いたものだけを置く。

### 後回し（需要を見て）
- GeoParquet と GeoPackage（依存が重いので、入口を分けたうえで検討）
- WebGPU バックエンド、MapLibre Tile (MLT)
- ボクセル、ガウシアンスプラッティング、時間で動く 3D（CZML 相当）、COPC / LAZ の点群
- スタイルの部品化（imports・config・slots に当たるもの）、色の LUT
- rabbita 以外の UI ライブラリ向けの部品（§6）

### やらない（当面）
- Style Spec の完全互換、プラグイン機構、古いブラウザへの対応（WebGL2 と WebAssembly GC が要る）
- 組み立て済みの UI ウィジェット（見た目を持つ部品）。機能はヘッドレスな API で渡し、作り方は example で示す
- サーバー側の機能が欠かせないもの：タイル配信、データベース、認証（ポータル、OAuth）、編集結果の保存と同期、ジオコーディングやルート探索・到達圏のサービス、ジオエンリッチメント、画像サーバーの解析、ストリーミング。ライブラリはブラウザ内で完結させ、保存や共有は利用者のアプリに任せる
  - 外部のサービスにつなぐ部分は、**差し替えられる口**（GeoSearch のプロバイダ、`transformRequest` など）だけを用意する。特定のサービスを既定にしない
  - 標準の形式のタイルやデータ（XYZ、TileJSON、PMTiles、WMTS、OGC API）や、仕様が公開されている Web サービス（ArcGIS REST API、OGC の WMS・WFS など）を読むのは、データの読み込みとして扱う。どこから配るかは利用者が決める
  - 印刷はクライアントで完結させる（§8 の Phase 21）。サーバーで描き直さず、ブラウザで高解像度に描いて PDF にする
- ほかの GIS SDK の機能の網羅

## 6. API 方針

### スタイルの互換（方針 D、ユーザー判断）

- 既定では、未対応の式・値・プロパティがあっても地図を描く。そのプロパティは既定値に戻し、レイヤーそのものが描けないときだけ、そのレイヤーを外す。どれも警告（コンソールと、パス付きの一覧を持つイベント）で知らせる。
- `strict: true` を渡すと、未対応のあるスタイル全体を拒む。正確さを確かめたい作り手やテスト向け。
- 黙って無視するプロパティは作らない（必ず警告する）。
- 未対応のものは、MapLibre と同じに描けるよう可能なかぎり対応していく。いまの対応は [style-support.md](../style-support.md) にある。

### TS

MapLibre GL JS の API に**名前と形を寄せる**（移行しやすくするため）が、完全互換は目指さない。寄せた API は、同じ入力に同じ結果を返すことをゴールデン（`bench/`）で確かめる。

データ処理と解析は別の入口（`mbt-map/data`、`mbt-map/analysis` など）から使う。初回の呼び出しで Wasm を読み込み、Worker で実行して Promise を返す。結果は列指向の表で、`toGeoJSON()` で地図のソースになる。

### Web Component

- `<mbt-map style-url="..." center="139.76,35.68" zoom="12">` のように属性で初期化でき、プロパティで `map` インスタンスに触れる。属性は厳密に読み、不正な値は `mbt-map-error` で知らせて使わない。
- `mbt-map-move`、`mbt-map-load` などを `CustomEvent` で発火する。
- Shadow DOM の中に canvas を持つので、仮想 DOM 系のフレームワークからは「中身を触らない 1 要素」として扱える。これが UI フレームワークに依存しないことの要。

### MoonBit

- 中身（ファサード）は TS のまま、MoonBit には **npm の実装を中で使う型付きの API**（`moonbit/mbtmap`、js ターゲット）を出す。地図、カメラ、イベント、型付きのスタイルと式（MapLibre の style-spec から生成。JSON も渡せる）。ファサードを MoonBit に移す案は、メインのバンドルが大きくなるので取りやめた（PROGRESS.md）。MoonBit で書いた処理をメインのバンドルに入れるのは、描画のエンジンのように MoonBit で書く意味が大きいものに限る。
- カメラの状態は値として取得・設定でき、イベントは購読と解除ができる。
- UI ライブラリには、`<mbt-map>` を包む薄い部品で応える。いまあるのは rabbita 向けの `moonbit/mbtmap_rabbita`（要素を view に、イベントをメッセージに）。ほかのライブラリ向けは需要を見てから作り、**コアを特定の流儀に寄せない**。着手の前に、対象のライブラリの現行のソースで、外部の DOM とカスタム要素の扱いを確かめる。

### ヘッドレス UI

- 機能は**見た目を持たないコントローラ**として渡す。コントローラは、状態（値として取得できる）、操作（メソッド）、変化の通知（購読と解除）だけを持ち、DOM を作らない。描画が要るもの（作図中の線、計測の補助線、選択の強調）は、地図のレイヤーとして描く。
- 作り手は、状態を読んで好きな見た目（素の DOM、React、Vue、Svelte、Canvas など）で描き、ユーザーの操作をメソッドに渡す。キーボード操作や ARIA に要る状態（選択中の候補、展開中かどうかなど）もコントローラが持つ。
- コントローラは表示の入口（`mbt-map`）の公開 API だけを使い、内部に依存しない。表示だけを使う利用者のバンドルは増えない。コントローラごとに tree-shaking で落とせること。

- GeoSearch のプロバイダは `{ name, search(query, { signal, bbox, limit }), reverse?(lngLat) }` の形。既定は**サーバーに問い合わせない**もの（座標の読み取り、読み込んだデータの属性検索）。外部の検索 API は、同じ形のプロバイダとして作り手が足す（利用条件と出典表示は作り手の責任）。

## 7. 作業ルール

- **MoonBit の構文・ツールチェーンは変化が速い**。公式ドキュメント（docs.moonbitlang.com）、`moon ide doc`、生成される `.mbti` で確かめてから書く。記憶で API を推測しない。ツールチェーンの版は `scripts/toolchain.env` に固定する。
- `moon check`、`moon test`（全ターゲット）、`moon fmt`、`moon info` を通してからコミットする（AGENTS.md §1）。
- テストは**黄金データ**で：既存の実装の出力と突き合わせるスクリプトを `bench/` に置く。テッセレーションは、三角形の総面積が元のポリゴンと一致することも確かめる。
- テストデータは少数を、出典表記とともに fixtures にする（`NOTICE-dev.md`）。
- 段階ごとに PROGRESS.md を更新する：できたこと、計測の結果、既知の問題、次にやること。計画の文書は VISION.md と PROGRESS.md のほかに作らない。
- 大きな設計変更（Wasm バックエンドの選択、パッケージ分割の変更、描画方式の変更）と予算の変更は、計測結果と選択肢を示して**ユーザーに確認してから**進める。
- ライセンスは Apache-2.0。ほかの実装を移植するときは、元のライセンスと出典をファイルの先頭と `NOTICE` に書く（配布物に入るものは `NOTICE`、リポジトリの中だけで使うテストデータや比べる相手は `NOTICE-dev.md`）。依存を足す前に AGENTS.md §8.1 の確認をする。
- 公開する文書では、ほかのライブラリと張り合う書き方をしない。ベンチは前に出さない（PROGRESS.md「進め方と名前の決定」）。
